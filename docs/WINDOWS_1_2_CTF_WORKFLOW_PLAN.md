# Windows 1.2 — повседневная работа с CTF

Дата: 27 ноября 2026 г. Статус: начало разработки; не приёмка и не обещание даты.
База: опубликованная Windows 1.1.2, `f364df6` / PR #103–#104.

## Результат для пользователя

Открыть CTF → диск/папка/файл → заметка, теги и категория → закрыть/открыть →
внешнее сохранение в WhereIsIt → сохранённые правки либо явный конфликт →
экспорт новой CTF-копии. Для назначения правок не нужен полный импорт каталога.
Поиск, дерево и аналитика остаются доступны с открытым metadata snapshot.

Текущее ограничение 1.1.2: прямой CTF-просмотр разрешает чтение, а аннотации и
категории требуют native-импорта. Существующие sidecar/annotation-модули надо
проинвентаризировать и переиспользовать после проверки; второй конкурирующий
источник правды не создавать. [ADR-0003](decisions/ADR-0003-ctf-authority-content-caches.md)
и [ADR-0005](decisions/ADR-0005-direct-ctf-metadata-search.md) сохраняют силу.

## Очередь и выходные критерии

| Этап | Статус | Поставка и критерий завершения |
|---|---|---|
| 1. PR58: полный сценарий | NEXT | В существующей композиции инспектор позволяет заметку/теги/категории CTF; состояния сохранения, ошибки, перезапуска и внешнего конфликта показаны на синтетике. Реальная браузерная демонстрация; native-перенос только после этого checkpoint. |
| 2. Контракт и долговечное хранение | NEXT | Аудит существующего кода; документ/поколение/запись/ревизия правки имеют явную идентичность. SQLite-журнал не является кэшем. Атомарное сохранение, повтор операции, устаревшая ревизия, rollback/backup и конфликт протестированы на синтетике. |
| 3. Rust/service и egui | PLANNED | Тот же UX PR58 работает поверх прямого CTF snapshot; чтение и поиск учитывают применимые правки. Сохранение одного файла не вызывает полный импорт, полную копию строк или блокировку UI. Перезапуск сохраняет заметки/теги/категории и контекст. |
| 4. Внешнее изменение | PLANNED | Новое поколение CTF определяется независимо от имени/mtime/размера. Переименование, перемещение, вставка, удаление, дубли и смена порядка не приклеивают правки к чужим строкам. Однозначные случаи переносятся по проверяемой идентичности; неоднозначные/осиротевшие остаются доступными конфликтами. Пользователь выбирает решение; старые поколения и правки сохраняются. |
| 5. Экспорт и обмен | PLANNED | Новая копия CTF получает представимые принятые изменения; неизвестные данные сохраняются. Непредставимые теги/категории остаются в долговечном слое и явно перечисляются в политике экспорта/резервной копии. Нет молчаливого lossy export. Изменённая копия открывается оригинальной WhereIsIt; её внешнее Save As повторно читается нашим приложением. |
| 6. Приёмка и Windows stable | PLANNED | Точный hosted-установщик, полный сквозной сценарий и копия большого CTF, отмена/повтор, конфликт, восстановление, offline, обновление с 1.1.2 и сохранность внешних данных. Затем тег и stable; старые файлы неизменны. |

Этапы 1 и 2 могут идти параллельно. Native UX этапа 3 не проектируется отдельно
от прототипа. Субагенты получают ограниченные области; root интегрирует и
сохраняет итоговые артефакты. Статусы меняются по наблюдаемому результату.

## Граница хранения и безопасности

- Исходный CTF только для чтения, экспорт в новый файл. Разработка и QA — на копиях.
- У документа есть долговечная идентичность; одинаковые байты двух копий не
  объединяют их личные правки автоматически. Хеш поколения подтверждает версию,
  но не доказывает соответствие записей между поколениями.
- Не использовать индекс строки/offset как устойчивую идентичность после внешней
  правки. Даже путь+имя не разрешают неоднозначность дублей автоматически.
- Поисковые ускорители удаляемы и пересоздаваемы; аннотации, категории, журнал и
  решения конфликтов — пользовательские данные с отдельным backup/restore.
- Модель категорий и поиск по заметкам/тегам имеют одинаковую семантику в snapshot,
  SQLite и экспортируемой выборке. Для неизвестной CTF-семантики — явная диагностика.
- Прерывание сохранения/экспорта и смена источника не публикуют частичное состояние.

## Что измеряем

На неизменённой копии полного каталога отдельно измеряются открытие/первый поиск,
сохранение одной правки, повторное открытие с правками, фильтр по заметке/тегу/
категории, память и стоимость смены поколения. Сравнение с 1.1.2 — одинаковым
workload; сервисные числа и GUI-наблюдения не смешиваются. Сначала фиксируется
baseline; числовые бюджеты обосновываются измерением, без выдуманного SLO.

## Вне этого выпуска

macOS/Linux product release, USB pairing/rescan, подпись, видеосигнатуры,
универсальный DuckDB-переезд и общая сортировка. Дополнительное уплотнение памяти
или новый индекс вводятся только при измеренном препятствии этому сценарию.

## Проверки и публикация

Для каждого изменения — тесты затронутой целостности/семантики/отмены; общий
переносимый CI сохраняется. Полная установленная проверка связывается с кандидатом
релиза, а не повторяется как самостоятельная цель после каждого документа.
До наблюдаемой приёмки следующего кандидата его `stable_ready=false`.
Версия опубликованной 1.1.2 и её acceptance не переписываются.
